# ParkMaster 제품 발전 계획

작성일: 2026-07-29
판단 기준: 사용성, 실용성, 실무 완료율, 신뢰성

## 1. 목표

ParkMaster를 기능이 많은 주차장 정보 시스템에서 다음 능력을 갖춘 실무 운영 시스템으로 발전시킨다.

> 해야 할 일을 발견하고, 담당자를 정하고, 기한 안에 조치하고, 증빙과 결재를 남기고, 결과를 다시 운영 개선에 사용하는 시스템

핵심 제품 지표는 **엑셀, 메신저, 수기 재입력 없이 ParkMaster 안에서 처음부터 끝까지 완료된 업무의 비율**이다.

## 2. 요약 진단

ParkMaster는 90개 이상의 라우트와 주차장, 조사, 운영, 시설, 수입, 예산, 입찰, 용역, 민원, 기획, 센서, 보고서, 결재 기능을 보유한다. 데이터 범위와 화면 수는 이미 충분하다.

현재 가장 큰 문제는 기능 부족보다 업무 연결과 신뢰성이다.

1. 홈은 총 주차장, 주차면, 유형 같은 현황 중심이며 사용자가 오늘 처리할 업무를 알려주지 않는다.
2. 민원은 담당자, 기한, SLA, 상태가 연결된 가장 완성도 높은 실무 흐름이다.
3. 유지보수는 칸반 상태가 있지만 `배정`이 실제 작업자 지정과 통지로 이어지지 않는다.
4. 결재는 도메인 상태를 직접 변경하는 방식과 `approval_records/steps` 기반 방식이 동시에 존재한다.
5. 상태 전이 규칙은 코드에 있으나 실제 화면 변경에 강제되지 않는다.
6. 다중 테이블 변경이 브라우저에서 순차 실행되어 중간 실패 시 상태가 어긋날 수 있다.
7. 오프라인 조사, 메시지 발송, 예약 보고서 등은 기반 코드나 UI는 있으나 실제 실행 흐름이 닫히지 않았다.
8. 네이버 지도 SDK 인증 실패가 지도 영역이 아닌 홈 전체를 중단시키는 실행 오류가 확인됐다.

결론적으로 **새 모듈을 추가하기 전에 핵심 업무의 소유권, 기한, 다음 행동, 상태 무결성, 실패 복구를 공통 기반으로 만들어야 한다.**

## 5. 제품 원칙

1. 홈의 첫 질문은 `전체가 몇 개인가`가 아니라 `내가 지금 무엇을 해야 하는가`여야 한다.
2. 모든 실무 건은 가능한 범위에서 담당자, 상태, 우선순위, 기한, 다음 행동, 완료 증빙을 가진다.
3. 알림은 읽고 끝나는 메시지가 아니라 해당 업무의 정확한 행동으로 이동해야 한다.
4. 지도는 네이버만 사용하되 지도 장애가 비지도 업무를 중단시키지 않아야 한다.
5. 한 화면의 상태 변경이 여러 레코드를 바꿀 때는 DB 함수 또는 서버 명령으로 원자적으로 처리한다.
6. 모바일에서는 조회 축소판이 아니라 촬영, 체크, 서명, 임시저장, 재동기화를 완결한다.
7. AI는 검증 가능한 업무 비용을 줄일 때만 사용한다. 출처, 검토, 취소, 비AI 대체 경로를 제공한다.

## 6. 우선순위

점수는 빈도, 시간 절감, 위험 감소, 적용 범위, 도입 용이성, 근거 강도를 가중 합산한 뒤 개발 난이도로 나눈 잠정값이다. 운영자 인터뷰와 실제 사용 로그로 다시 계산한다.

| 순위 | 기회 | 우선도 | 판단 |
|---:|---|---:|---|
| P0 | 네이버 지도 실패 격리와 홈 복구 | P0 예외 | 현재 핵심 화면 전체가 중단되는 실행 오류 |
| P0 | 결재/상태 변경의 권한, 원자성, 전이 규칙 통합 | P0 예외 | 데이터와 감사 이력 신뢰성 문제 |
| P0 | 민원 개인정보 접근 제한과 기한 초과 정합성 | P0 예외 | 민감정보 노출 가능성과 실제 초과 업무 누락 위험 |
| 1 | 역할별 `내 업무`와 예외 중심 홈 | 1.48 | 전체 모듈의 일상 업무 발견 시간을 줄임 |
| 2 | Parking Lot 360을 업무 허브로 강화 | 1.40 | 이미 있는 연결 기반을 활용해 탐색과 재입력 감소 |
| 3 | 유지보수 작업지시와 예방정비 자동 생성 | 1.38 | 고장 대응과 현장 업무의 책임 및 완료 증빙 강화 |
| 4 | 보고서/엑셀 입출력의 실제 실행화 | 1.23 | 행정 보고와 반복 데이터 이동 시간을 직접 절감 |
| 5 | 수입 누락 확인, 대사, 월 마감 잠금 | 1.11 | 재정 오류와 마감 지연 위험이 큼 |
| 6 | 통합 결재 엔진과 업무별 결재 연결 | 1.08 | 승인 우회와 불일치를 제거 |
| 7 | 현장 모바일 및 오프라인 완결 | 1.03 | 사무실 재입력과 현장 데이터 손실 감소 |
| 8 | 용역 성과물, 검수, 보완, 지급 연결 | 0.90 | 계약 이행과 지급 통제를 시스템 안에서 완결 |
| 9 | IoT 이상을 유지보수 작업으로 자동 전환 | 0.80 | 센서 관제를 실제 복구 업무로 연결 |

민원 SLA 자동 감시와 에스컬레이션은 구현 난이도가 낮고 효과가 높아 `내 업무`의 첫 적용 도메인에 포함한다.

## 7. 단계별 로드맵

### Phase 0. 신뢰성 기반, 0-4주

목표: 사용자가 핵심 화면에 들어갈 수 있고, 한 번의 결정이 안전하게 한 번만 반영되게 한다.

의존성: Supabase 마이그레이션 권한, 역할 정책 합의, 네이버 NCP Dynamic Map과 허용 URL 설정
비목표: 새 업무 모듈 추가, 전체 UI 개편

- 네이버 지도 SDK/타일 실패를 지도 영역 안에서 격리하고 목록/업무 기능은 계속 제공한다.
- 잘못된 결재 조회 필드와 빈 큐 문제를 바로잡는다.
- 조사 승인/반려를 권한 검사, 전이 검사, 중복 방지, 알림, 감사기록까지 포함한 단일 DB 명령으로 만든다.
- 모듈 라이선스와 역할을 라우트, 버튼, RLS에서 같은 규칙으로 적용한다.
- 핵심 상태 변경에 서버 측 전이 검증을 적용한다.
- 최소 E2E 테스트를 `조사 제출 -> 결재함 -> 승인/반려`에 추가한다.
- 업무 발견 시간, 기한 초과율, 미배정률의 기준값을 계측한다.

종료 조건:

- 알려진 홈 크래시 0건
- 권한별 직접 URL/RPC 테스트 통과
- 조사 승인 시 조사, 주차장 반영, 알림, 감사기록이 모두 성공하거나 모두 롤백
- 결재 큐 조회 오류 0건
- 핵심 흐름 브라우저 E2E 통과

### Phase 1. 매일 쓰는 업무 도구, 1-3개월

목표: 로그인 후 30초 안에 오늘 할 일을 파악하고 바로 처리한다.

의존성: Phase 0의 명령/권한 표준, 실제 부서와 담당 체계 확인, 기준 지표 수집
비목표: 기존 모든 도메인을 한 번에 공통 `work_items` 테이블로 이전

- 역할별 `내 업무`: 긴급, 기한 초과, 오늘 마감, 미배정, 결재 대기, 차단됨
- 첫 적용: 민원, 유지보수, 예방점검, 조사 검토, 결재
- 유지보수 배정 시 실제 담당자 선택, 알림, 착수, 부품 대기, 완료, 독립 검증
- 예방정비 일정에서 작업지시 자동 생성 및 다음 주기 갱신
- 민원 SLA의 시간 기반 재계산, 사전 경고, 팀장 에스컬레이션
- Parking Lot 360에 `진행 중 업무` 타임라인과 빠른 등록/이동 제공
- 현장 조사 임시저장, 오프라인 큐, 충돌 처리, 사진 재전송 구현

종료 조건:

- 진행 업무의 90% 이상에 담당자와 기한 존재
- 사용자별 첫 행동 도달 시간 30초 이하
- 기한 초과 민원 20% 감소
- 조사 동기화 성공률 95% 이상
- 유지보수 MTTA와 MTTR 기준선 대비 감소

### Phase 2. 재정과 계약 통제, 3-6개월

목표: 마감과 계약 이행을 별도 엑셀 없이 통제한다.

의존성: 원천 수입/정산 파일 형식, 통합 결재 표준, 증빙 보관 정책
비목표: 회계 ERP 전체 대체, 기관별 모든 외부 시스템의 동시 연동

- 일별 수입 누락 주차장/일자 자동 검출
- 카드/현금/운영사 자료 가져오기와 검증 실패 목록
- 차이 임계값, 사유, 증빙, 검증자, 기간 마감 잠금
- 입찰 계약에서 용역 사업 자동 생성 및 필드 매핑
- 성과물, 검사, 보완 요구, 재검사, 지급 요청, 결재 연결
- 실제 PDF/Excel 생성, 예약 실행, 전달 성공/실패 추적

종료 조건:

- 월 마감 3영업일 이내
- 미확인 수입 누락 0건
- 결재 평균 소요시간 30% 감소
- 용역 마일스톤과 검사의 90% 이상 시스템 내 처리

### Phase 3. 생애주기 자동화, 6-12개월

목표: 감지에서 조치, 계획에서 운영 전환까지 연결한다.

의존성: 신뢰 가능한 센서 수집 경계, 충분한 운영 이력, 작업지시와 보고서 실행 기반
비목표: 무인 의사결정, 근거 없는 예측, 사람 검토가 없는 AI 자동 실행

- 센서 이상 중복 제거, 담당자 통지, 유지보수 작업 자동 생성, 복구 확인
- 후보부지 선정, 사업 시작, 입찰, 준공 점검, 주차장 등록 연결
- 운영 성과와 위험 중심의 관리자 화면
- 충분한 데이터가 쌓인 영역에 한해 AI 요약, 이상 설명, 보고서 초안 적용

종료 조건:

- 센서 장애 MTTR 25% 감소
- 예약 보고서 성공률 98% 이상
- 준공 후 운영 등록까지의 수작업 재입력 제거

## 8. 첫 개발 단위

첫 제품 단위는 **안전한 민원 분류와 담당자 인수: 접수에서 담당 확정까지**로 한다. 실제 일상 업무 빈도가 높고, 기한 판단 오류와 미배정, 개인정보 접근을 한 번에 개선할 수 있다.

네이버 지도 실패 격리와 결재 조회 스키마 수정은 이 단위보다 먼저 또는 같은 배포의 P0 핫픽스로 처리한다. 조사 승인 원자 명령은 바로 다음 단위로 진행해 전체 결재 표준을 세운다.

### 사용자 시나리오

권한이 있는 민원 담당자가 로그인하면 미배정, 긴급, 기한 초과, 내 담당 민원을 정확히 확인한다. 한 건을 직접 인수하거나 다른 담당자에게 배정하면 담당자, 상태, 알림, 감사 이력이 한 번의 명령으로 반영되고 해당 담당자는 바로 처리를 시작한다.

### 포함 범위

- 현재 날짜와 `due_date`로 초과 여부를 일관되게 계산
- 미배정, 긴급, 기한 초과, 내 담당 필터
- 역할/팀/담당 범위에 따른 민원 개인정보 조회 제한
- `claim` 또는 `assign` DB RPC/서버 명령
- 담당자, 상태, 알림, 감사기록의 원자 처리
- 동시 인수 시 한 명만 성공하도록 충돌 제어
- 성공 후 `내 업무`와 민원 목록 즉시 갱신
- 모바일에서 담당자, 상태, 기한, 다음 행동이 첫 화면에 노출

### 제외 범위

- 전체 모듈 통합 `내 업무`
- 민원 AI 답변 작성
- 일괄 자동 배정과 조직 최적화
- 유지보수 작업지시 개편

### 인수 조건

1. 같은 민원은 목록, 상세, KPI에서 동일한 초과 판단을 보인다.
2. 권한이 없는 역할은 UI와 직접 쿼리/RPC 모두에서 민원 개인정보를 읽을 수 없다.
3. 인수/배정 성공 시 담당자, 상태, 알림, 감사기록이 모두 반영되거나 모두 롤백된다.
4. 두 사용자가 동시에 인수하면 한 명만 성공하고 다른 사용자는 최신 담당자를 확인한다.
5. 담당자는 배정 직후 `내 업무`에서 민원을 확인하고 처리를 시작할 수 있다.
6. 375px 모바일 화면에서 담당자, 기한, 상태, 주 행동이 가려지지 않는다.
7. 접수부터 담당 확정까지 권한별 브라우저 테스트가 통과한다.

## 10. 검증이 필요한 가정

- 실제 부서와 담당 체계가 현재 `operations/facilities/planning/admin` 네 팀보다 세분화되어 있는가?
- 담당자는 ParkMaster를 매일 여는가, 아니면 메신저/엑셀 지시 후 결과만 입력하는가?
- 유지보수 작업자는 내부 직원인가, 외부 업체인가, 혼합인가?
- 현장의 네트워크 단절 빈도와 사진 용량은 어느 수준인가?
- 수입 원천 시스템과 운영사 정산 파일 형식은 무엇인가?
- 승인 단계와 직무 분리는 기관별로 얼마나 다른가?
- 성과를 비교할 수 있는 실제 처리시간, 초과, 재오픈, 마감 데이터가 충분한가?

이 항목은 개발을 멈추기 위한 질문이 아니라, Phase 0 계측과 5명 내외의 대표 사용자 인터뷰로 우선순위를 보정하기 위한 목록이다.
