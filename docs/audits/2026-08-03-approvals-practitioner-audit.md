# 결재함 실무자 검증 및 개선 보고서

- 관찰 환경: 로컬 런타임 + 연결된 Supabase 데모 데이터
- 관찰 시각: 2026-08-03 16:58 KST
- 대상 사용자: 제주시청 차량관리과 운영팀 주무관, 팀장, 관리자
- 핵심 업무: 결재 대상을 찾고 원업무와 공식 문서를 확인한 뒤 승인·반려하고, 결과가 원업무에 반영됐음을 확인한다.

## 실행 진단

기존 결재함은 원업무 테이블의 상태와 정식 결재 레코드를 혼합하면서 승인 완료된 용역 지급도 대기로 표시했고, 검색·정렬·반려 사유·문서 연결 상태가 부족했다. 개선 후 실제 데이터 기준 결재 대기 15건 중 처리 가능 12건, 문서 미연계 14건, 연계 이상 3건을 구분해 보여준다. 승인 전 원업무와 문서번호를 한 화면에서 확인할 수 있고, 조사·예산·입찰·용역별 결과 상태를 각 업무 규칙에 맞게 반영한다.

## 구현한 개선

- 정식 결재와 원업무 대기를 중복 제거해 통합 표시한다.
- 승인 가능 건, 대기 금액, 문서 미연계, 연계 이상을 별도로 집계한다.
- 공식 문서번호와 원업무 이동을 결재 건에 직접 제공한다.
- 반려 사유를 필수화하고 일괄 승인은 같은 업무·테이블만 허용한다.
- 조사·용역 검수·용역 지급은 도메인 명령을 사용하고 예산 집행 승인은 `executed`로 전환한다.
- 승인·반려 활동 로그를 기록하고 중복 클릭을 조건부 갱신으로 방지한다.
- 지정 결재자가 있는 단계는 해당 사용자만 처리할 수 있다.
- 기본 결재선과 진행 중 결재의 중복을 막는 DB 마이그레이션을 추가했다.
- 결재 대화상자 설명과 모바일 터치 영역을 보완했다.

## 지표 계약

- 이벤트: 결재 대기 항목을 열어 원업무·문서를 확인하고 최종 처리
- 대상: 처리 권한이 있는 결재 건
- 기준값: 데모에서 목록 확인부터 처리까지 2개 화면, 문서 미연계 14/15건
- 목표: 문서 연계율 100%, 원업무 결과 불일치 0건, 정상 건 처리 3화면 이내
- 데이터 원천: `approval_records`, `approval_steps`, 원업무 테이블, `activity_logs`, 공식 문서 링크
- 주의: 데모 데이터는 동작 검증 근거이며 운영 성과 기준선은 실제 배포 후 별도 수집한다.

## 잔여 위험

- `20260803165000_approval_line_integrity.sql`은 생성했으나 로컬 Supabase CLI 인증 토큰이 없어 원격 DB에는 아직 적용하지 못했다. 배포 파이프라인에서 적용해야 한다.
- 정식 결재 단계 변경·원업무 변경·활동 로그는 아직 하나의 DB 트랜잭션이 아니다. 현재 정식 데모 고아 레코드는 처리 불가로 차단했지만 통합 RPC가 필요하다.
- 예산 집행 신규 등록은 승인된 예산 계획이 없어 예산항목을 선택할 수 없었다. 예산관리 메뉴 검증 단계에서 샘플 계획과 등록 흐름을 보완한다.
- 회수 사유·재상신과 모든 업무의 내 요청 표준화는 후속 결재 워크플로 공통 기반 작업으로 남는다.
